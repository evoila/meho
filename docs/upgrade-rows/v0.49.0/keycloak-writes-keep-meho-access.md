## Note
In MEHO's own login realm, MEHO now refuses a Keycloak write that would take MEHO's own access away: a write that disables, deletes or locks out a login MEHO itself uses (the service-account user of `KEYCLOAK_ADMIN_CLIENT_ID` or `CHECK_RUNNER_CLIENT_ID`), the last active platform admin, or the account that asks. Adding a required action to your own account is refused too. Removing the last active platform admin from a group, deleting a group, or changing a group's attributes is refused when it takes the platform admin rights of the last active platform admin. MEHO counts a person as a platform admin as its login does: the user's own `platform_admin` value, else the value of the user's groups; a group's name gives no rights. Another person counts only through an attribute named exactly `platform_admin`; an attribute in another letter case, or named in `JWT_PLATFORM_ADMIN_CLAIM_NAME`, makes no other person count. Such a write is also refused when the other platform admins have the rights only from their own user attribute: MEHO counts the others through the groups that give the rights. MEHO refuses before the request waits for approval and again when it runs, also under a standing grant, and refuses when a Keycloak read fails. Two such writes run one after the other, also across pods. With `JWT_PLATFORM_ADMIN_ROLE_NAME` set, such a write on a platform admin, and such a group write, is refused. A request that waits for approval from before the upgrade is refused when it runs if it hits one of these cases.

## Action
Keep at least two people with platform admin rights from a group whose `platform_admin` attribute is `true`. To replace a login MEHO uses, set up the new login in MEHO's settings first. No schema action.

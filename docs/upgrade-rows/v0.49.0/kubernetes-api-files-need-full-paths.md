## Note
MEHO refuses to load an API file whose paths look like Kubernetes paths without `/api/v1` or `/apis/<group>/<version>`, for example `/namespaces/{namespace}/secrets` or `/apps/v1/namespaces/{namespace}/deployments`. The next ingest of an existing connector made from such a file is refused too. Operations already stored from such a file are not deleted or changed. Each of their calls now waits for a person where the same call on the full path waits: a write of an object, a Secret, a pod's `exec`, `attach`, `portforward` or `proxy`, and a ServiceAccount token. No grant, agent grant or run approval covers those calls. At start, MEHO writes one warning log line `short_kubernetes_paths_stored` for each connector with such operations.

## Action
Look for the warning `short_kubernetes_paths_stored` in the server log. Or list the generic connectors with `meho connector list`, and check the op ids of each Kubernetes one with `meho operation search` for op ids whose path starts with `/namespaces/` or with a group and version. Find the grants, agent grants and run approvals that name them with `meho service-principals grants list`, `meho agent grant list` and `meho approvals runs list`, and remove them: they do not cover these calls. Plan for a person to approve each such call. Then load the standard API file that the cluster serves, or write the start in the file's server address as a relative path (for example `/api/v1`) and put the host in the target address. No schema action.

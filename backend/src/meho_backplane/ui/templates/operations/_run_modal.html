{#- SPDX-License-Identifier: Apache-2.0 Copyright (c) 2026 evoila Group Operation run-confirm modal fragment (Initiative #1835 G10.9, Task #1881). Swapped into ``#operations-drawer-container`` by the detail drawer's Run button (``hx-get /ui/operations/run/{descriptor_id}``). This is the console's highest-blast-radius surface: confirming dispatches a REAL connector op against a live target. The safety gate must be UNMISSABLE. The confirm POST carries the OWASP signed double-submit CSRF token on the confirm button's OWN ``hx-headers`` (HTMX does not inherit ``hx-headers`` to children -- the element that issues the request must carry it). The run GET minted the token + re-set the matching ``meho_csrf`` cookie. The confirm button disables itself during dispatch (``hx-disabled-elt``) so a high-impact op cannot be double-fired. The result swaps into ``#operations-run-result-region`` inside this modal (``operations/_result.html``); the modal stays open so the operator reads the OperationResult / the awaiting_approval deep-link in place. Run is in the OPERATOR capability set -- no tenant_admin step. The policy gate (NOT RBAC) is what escalates a ``requires_approval`` op to ``awaiting_approval`` once dispatched. A ``destructive`` op (a delete that cannot be undone) gets a preview step inside the form (#5015). MEHO stores the approval request for such an op only when the run carries the ``preview_hash`` of a preview of the exact same call (#3197). The Preview button posts the form to ``/ui/operations/preview``; the preview fragment carries a hidden ``preview_hash`` input, so the next Run sends it. Editing the target or the params clears the preview, so a stale hash is never sent.

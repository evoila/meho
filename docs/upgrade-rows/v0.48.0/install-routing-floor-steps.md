## Note
With `POLICY_CLASSIFICATION` on, a step of a multi-step operation now reads the category and labels of an override of its operation, like a direct call. This changes a step also while `POLICY_APPROVER_ROUTING` is off. With `POLICY_APPROVER_ROUTING` on too, a step waits for the same approvers as a direct call. The approval card, the "may approve" sign, the bell count and the push messages now use the install's current routing, as the approve click does. The audit row of an approval names the install entry that counted (`approver_floor`). A tenant policy import no longer refuses a wider routing entry in two cases, it warns instead: when an earlier entry of the same tenant fits each of its changes first, and when both connector patterns have a wildcard and differ. `meho policy export` of a tenant writes a `# Has no effect where wider:` comment above a routing entry that is wider than the install's. A request with routed approvers but no stored install category (it started to wait while `POLICY_CLASSIFICATION` was off, or an older build of main wrote it) counts as "category not known" while `POLICY_CLASSIFICATION` is on. No schema migration.

## Action
If `POLICY_CLASSIFICATION` is on, a step of a multi-step operation can now wait for approval, also while `POLICY_APPROVER_ROUTING` is off. Nothing else to do while `POLICY_APPROVER_ROUTING` is off. Otherwise reject a waiting request that the click now refuses because MEHO does not know its category, and start the call again. See [The install's routing is a floor](https://evoila.github.io/meho/latest/guides/policy-file/#the-installs-routing-is-a-floor).

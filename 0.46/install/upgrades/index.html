    Upgrades¶

    MEHO upgrades are a standard helm upgrade with two things worth understanding before your first one: migrations run before the new version rolls, and Helm 4's server-side apply can surface field-ownership conflicts on clusters where someone once hand-patched the Deployment.

    What helm upgrade does¶

    helm upgrade meho oci://ghcr.io/evoila/meho-chart \
  --version <chart-version> -n meho -f values.yaml
    1. The pre-upgrade migration Job runs every pending database migration first. If a migration fails, the release fails and the old Pods keep serving — an unmigrated schema never meets a new application version. Failed Jobs are retained for ten minutes for kubectl logs.
    2. Only after migrations succeed does the new Deployment roll.
    3. The old Pod stops before the new Pod starts (update strategy Recreate). Old and new code never share the database. The old Pod keeps serving for 5 seconds, so no request runs into a closed Pod. Then it takes no new calls and lets running operations finish, for up to 60 seconds. An operation that still runs then is written to the audit log as unfinished: check its target before you run it again. Then the new Pod starts.

    What an update costs: about one to two minutes without MEHO: the drain of the old Pod plus the start of the new one. This is the price of never running two versions against one database. Plan updates for a quiet time, and tell the people who use MEHO. The values shutdown.drainSeconds and shutdown.preStopSleepSeconds set the two limits.

    An upgrade ends the approval requests that still wait. A person approves one exact release of MEHO, so when the new version starts, every request that waits from the older version expires with the reason "MEHO was updated; ask again". An approved request that has not run yet is refused and does not run. The requester asks again under the new version. Tell the people who wait for an approval before you upgrade.

    Keep the image tag pinned and immutable (v<x.y.z> or sha-<git-sha>) — :latest is never published, and :main is a moving dev alias, not a deploy target.

    Helm 4 field-ownership conflicts¶

    Helm 4 applies upgrades via Kubernetes server-side apply, which tracks who owns every field of every object. If an operator once hand-patched the live Deployment (kubectl patch / kubectl edit) with a field a newer chart now sets, the upgrade fails with:

    Apply failed with 1 conflict: conflict with "kubectl-patch"

    Pre-flight check — look for foreign field managers before upgrading:

    kubectl get deploy meho -n meho -o yaml --show-managed-fields \
  | grep 'manager:'

    Any manager other than Helm's own, owning a field the chart renders, will conflict. The remedy is to hand those fields to the chart:

    helm upgrade meho oci://ghcr.io/evoila/meho-chart \
  --version <chart-version> -n meho -f values.yaml --force-conflicts

    --force-conflicts overwrites the conflicting fields and transfers ownership to Helm. (Observed in the field: --take-ownership is not the right flag here — it adopts whole un-owned resources, not individual fields, and does not clear a per-field conflict.)

    Upgrade fails with spec.strategy.rollingUpdate: Forbidden¶

    From v0.46.0 the chart uses the Recreate update strategy: the old pod stops before the new one starts. An install made with an older chart has the strategy RollingUpdate on its live Deployment, with a rollingUpdate block that Kubernetes filled in. Helm 4 with server-side apply does not remove that block, and Kubernetes refuses it together with Recreate:

    Deployment.apps "meho" is invalid: spec.strategy.rollingUpdate: Forbidden: may not be specified when strategy `type` is 'Recreate'

    The chart fixes this itself. On such an upgrade it runs a short Job before the upgrade (<release>-…-update-strategy). The Job removes the block and sets Recreate on the live Deployment. No pod restarts for this. Helm removes the Job once it has succeeded. Helm 3 needs no Job: it removes the block on its own.

    If a revision already failed with this message (an upgrade to a chart built between v0.45.0 and this fix), the old pod still runs the old version. Check with helm history meho -n meho. Then:

    1. Run helm upgrade again with a chart that has the fix. The Job fixes the Deployment first, and the release ends deployed.
    2. If you must stay on the chart that failed, fix the Deployment by hand and run the same helm upgrade again:
    kubectl patch deployment meho -n meho --type=merge \
  -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
    1. Check the result. The release is deployed, and the Deployment has Recreate and no rollingUpdate block:
    helm status meho -n meho
kubectl get deploy meho -n meho -o jsonpath='{.spec.strategy}'

    Argo CD renders the chart with helm template, so it never runs this Job. With server-side apply on, run the kubectl patch above once, then sync.

    Later, back to RollingUpdate: the change above belongs to the field manager meho-update-strategy (or kubectl-patch). If you later set updateStrategy.type: RollingUpdate, Helm 4 reports a conflict with that manager. Use --force-conflicts, as in the section above.

    Rollback¶

    helm rollback meho is supported, with one asymmetry to know: migrations are forward-only. A rollback reverts the application version but not the schema — there is no automatic downgrade, so the older application runs against the newer schema and relies on the backend tolerating it. What "verified rollback" means precisely, and the schema-check fallback when it cannot be, is specified in the rollback acceptance contract.

    Every start writes the settings of the built-in operations into rows that all pods share. A start that fails changes none of them. A pod that started does change them, so during an update the old pod serves the new settings until it stops. GET /api/v1/health shows which release wrote the rows (operation_catalog). After a rollback, if it names another release, restart the pods you keep. The rollback contract above has the steps.

    When the new version does not start, MEHO is down, because the old Pod has already stopped. A start that fails changes no operation row, so roll back to the last good revision and wait for it:

    helm history meho -n meho
helm rollback meho <revision> -n meho --wait --timeout 10m

    Then check that /healthz answers and /version shows the previous release. The rollback contract has the full checklist.

    The bootstrap Job needs manage-realm¶

    This applies to the built-in Keycloak (coreKeycloak.enabled).

    After every install and upgrade, the bootstrap Job keeps the approval sign-in up to date: it makes the login flow meho approval sign-in level with the steps of the realm file, names the approval level in the realm, and binds the client meho-cli-approve to the flow. For this, its account meho-admin needs the realm-management role manage-realm. A new install gets the role from the realm file.

    An install whose first start was older, and had the company login off, may lack the role. What you see depends on when MEHO finds out.

    Before the upgrade (the usual case). Before an upgrade changes anything, a short Job checks that meho-admin has the role. Without it, the upgrade stops, and the version that runs now keeps running. Helm's error names the Job, and so the role:

    Error: UPGRADE FAILED: pre-upgrade hooks failed: ... job <release>-check-manage-realm failed ...

    The Job's log says what to do. The failed Job stays until the next upgrade, so you can read it at any time:

    kubectl -n <namespace> logs job/<release>-check-manage-realm

    core_bootstrap_failed: meho-admin lacks the realm-management role manage-realm, so the bootstrap Job would stop after the upgrade. The upgrade stops now and changes nothing. ...

    When the check cannot reach Keycloak, or cannot read the roles, its log says role check: unknown (...), and the upgrade goes on. Then the bootstrap Job checks again after the upgrade.

    After the upgrade. When the bootstrap Job still stops, the new version already runs. Without helm upgrade --atomic (for example with the Helm job of RKE2 or k3s), the release then ends as failed, and Helm says only:

    post-upgrade hooks failed: ... job <release>-core-bootstrap failed ...

    The reason is in the Job's log. The failed Job stays until the next install or upgrade:

    kubectl -n <namespace> logs job/<release>-core-bootstrap

    core_bootstrap_failed: login flow meho approval sign-in level: meho-admin may not read or change login flows, ...

    With helm upgrade --atomic, Helm rolls the release back when the Job stops, so the old version keeps running until you add the role.

    In both cases, give meho-admin the role once, then run the upgrade again:

    1. Log in to the Keycloak admin console as the console admin (The console admin) and pick realm meho. Lost every admin login? See Keycloak break-glass.
    2. Clients → meho-admin → Service account roles → Assign role → Filter by clients, search for realm-management, select manage-realm, Assign.
    3. Run helm upgrade again. The Job's log says login flow meho approval sign-in: kept (or created), and client meho-cli-approve: kept.

    Then check it: GET /api/v1/health shows approvals.sign_in.state: ok, and meho doctor shows approval sign-in as OK.

    With this role the backplane, which also uses meho-admin, can change the login settings of realm meho. It could already change people, groups and clients.

    Day-2 operations beyond upgrades¶

    Backup/restore and observability guides land on this site with MEHO's disaster-recovery workstream. Until then: PostgreSQL is MEHO's durable application store and the thing to back up first (see the reference architecture); the Valkey activity feed is ephemeral by design. For the knowledge store, see Back up and restore the knowledge store.

    A PostgreSQL restore alone does not rebuild a working deployment. The target credentials themselves live in Vault or Google Secret Manager, realm and client configuration lives in Keycloak, and your TLS Secrets and Helm values live in the cluster and in whatever you keep them under version control in. Each needs its own backup or reprovisioning path until the full guide lands.

    Back up and restore the knowledge store¶

    MEHO keeps its knowledge in the backplane database (PostgreSQL). One database backup holds all of it. There is no other copy.

    What the database holds¶

    What Where What it is
    Entries table documents, rows with source = 'kb' One row per entry. It holds the latest text and the metadata.
    Revisions table kb_revision One row per stored text of an entry. Older texts stay readable here.
    Passages and embeddings table documents, rows with source = 'kb-passage' The pieces of text that search ranks, with their embeddings. An embedding is a list of numbers for search by meaning. It is stored with the pgvector extension.

    The tenant settings file is not a backup of the knowledge store. It holds policies, conventions and targets, and no knowledge. See Backup and the settings.

    Take a backup¶

    Run pg_dump against the backplane database, with the custom format. Run it from a machine or pod that has the PostgreSQL client tools. Use the same major version as the server, or a newer one:

    pg_dump --format=custom --file=meho-backplane.dump \
  "postgresql://<user>@<host>:5432/<database>"

    Store the file somewhere that survives the loss of the server. Take the backup on a schedule, and take one before each upgrade.

    Restore into an empty database¶

    1. Create an empty database on a PostgreSQL server where the vector extension is available (the database image of the MEHO chart has it).
    2. Restore the dump into it:
    createdb -h <host> -U <user> <new-database>
pg_restore --no-owner --exit-on-error \
  --dbname="postgresql://<user>@<host>:5432/<new-database>" \
  meho-backplane.dump

    The dump contains the line that creates the vector extension, so the restore creates it. If your database user may not create extensions, ask a database administrator to run CREATE EXTENSION vector; in the new database first, and leave out --exit-on-error. pg_restore then reports one "already exists" error for that line. It is safe to ignore. 3. Point MEHO at the new database (the DATABASE_URL setting) and start it.

    A restore of the database alone does not bring back credentials, Keycloak or the Helm values. See the notes above.

    Check after a restore¶

    Pick one entry that you know:

    1. The entry: meho kb show <slug> returns the latest text.
    2. Its revisions: in the new database, this lists every stored text:
    SELECT r.revision_number, left(r.body, 60)
FROM kb_revision r JOIN documents d ON d.id = r.entry_id
WHERE d.source = 'kb' AND d.source_id = '<slug>'
ORDER BY r.revision_number;

    An agent reads one older text through the MCP resource meho://kb/id/<entry>/revision/<revision>. 3. A search hit: meho kb search "<words from that entry>" lists the entry.

    A test in the MEHO code (test_kb_backup_restore_pg.py) takes a dump with pg_dump, restores it with pg_restore, and checks the same three things.

    If the restored MEHO uses another embedding model¶

    The dump keeps the embeddings that the old model made. Search compares the question, which the new model embeds, with these stored numbers. Numbers from two different models do not match well, so search results get worse.

    To fix it, write each entry again with the same text. MEHO sees that the passages came from another model and builds them again. The easiest way is meho kb ingest over the source files of your entries. An entry that has no source file can be written again with meho kb add <slug> --body @<file>.

    A new model must give vectors of the same size (384 numbers). The database column has that size fixed. A model with another size needs a database migration first.

## Note
With `POLICY_APPROVER_ROUTING` on, the install's approver routing now holds the same way for a step of a multi-step operation as for a direct call: with `POLICY_CLASSIFICATION` on, the step reads the category of an override of its operation too. The approval card, the "may approve" sign, the bell count and the push messages now use the install's current routing, as the approve click does. The audit row of an approval names the install entry that counted (`approver_floor`). A tenant policy import no longer refuses a wider routing entry in two cases, it warns instead: when an earlier entry of the same tenant fits each of its changes first, and when both connector patterns have a wildcard and differ. `meho policy export` of a tenant writes a `# Has no effect where wider:` comment above a routing entry that is wider than the install's. A request with routed approvers but no stored install category counts as "category not known" while `POLICY_CLASSIFICATION` is on. No schema migration.

## Action
**Nothing to do** while `POLICY_APPROVER_ROUTING` is off. Otherwise reject a waiting request that the click now refuses because MEHO does not know its category, and start the call again. See [The install's routing is a floor](https://evoila.github.io/meho/latest/guides/policy-file/#the-installs-routing-is-a-floor).

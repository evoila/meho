## Note
**Action needed (service logins and run approvals).** These Keycloak writes are changes of rights, in every realm: `keycloak.realm.create`, `keycloak.realm.update`, `keycloak.client.create`, `keycloak.client.update`, `keycloak.client_scope.create`, `keycloak.client_scope.protocol_mapper.update`, `keycloak.protocol_mapper.create`, `keycloak.user.create`, `keycloak.user.update`, `keycloak.user.enable`, `keycloak.user.reset_password`, `keycloak.user.required_actions.update`, `keycloak.user.credential.delete`, `keycloak.role_mapping.assign`, `keycloak.role_mapping.client.assign`, `keycloak.group.member.add`, `keycloak.group.update_attributes`, `keycloak.authflow.ensure_approval_flow`, `keycloak.authflow.ensure_approval_touch` and `keycloak.authflow.ensure_passkey_code_skip`. Another admin (a tenant admin or a platform admin) must approve each call. The requester never approves their own request, and a MEHO-SA-Operator who is not an admin cannot approve it. A standing grant, an older grant row and a run approval do not cover them, a new grant or run approval that names one of them is refused, and no operation setting turns their approval off: an edit that tries is refused, and an override row with approval off does not count. This holds for every operation that is registered as a change of rights. A request that waits for approval at the upgrade follows the new rule. An install with one admin cannot get these writes approved until it has a second admin. The approval card of `keycloak.client.update` and `keycloak.realm.update` shows the values now next to the new values, and the card of `keycloak.protocol_mapper.create` shows the client's mappers now and the new one. Secret fields stay hidden. What `preview_operation`, `meho_approvals_get` and `meho_approvals_list` give back to the caller for these three writes is behind the new switch `KEYCLOAK_RIGHTS_CHANGE_CARDS` (off by default). When `keycloak.group.member.add`, `keycloak.role_mapping.assign`, `keycloak.role_mapping.client.assign`, `keycloak.user.update`, `keycloak.user.credential.delete` or `keycloak.group.update_attributes` waits for approval, MEHO reads the realm name from Keycloak (`GET /admin/realms/{realm}`) to see whether the target is MEHO's own login realm. When that read fails, MEHO treats the realm as its own login realm, and the stricter approver rules of that realm apply.

## Action
A service account or an agent that ran these writes under a grant or a run approval now waits for a person on each call. Ask another admin to approve them in the console or the CLI. Remove grant rows that name them; they clear nothing. An install with one admin adds a second admin in Keycloak itself (in `MEHO-Admins` or `MEHO-Platform-Admins`) before it runs these writes. To give these tools the same cards, set the switch with Helm: `extraEnv: [{name: KEYCLOAK_RIGHTS_CHANGE_CARDS, value: "true"}]`. **Your own Keycloak:** give MEHO's Keycloak admin client the realm-management role `view-realm`, so it can read the realm. No schema action.

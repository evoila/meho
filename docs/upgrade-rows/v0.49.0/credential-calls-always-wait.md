## Note
A call that reads, writes or makes a credential (the classes `credential_read`, `credential_write` and `credential_mint`, for example `vault.kv.put`, `vault.token.create` or `vault.kv.generate`) waits for a person on every call. No standing grant, no agent grant and no run approval covers it, also one made before the upgrade: such a grant stays stored, but each call waits. The call of an agent or a service login of such an operation waits also at level `safe`, and the approval of a parent multi-step run does not cover such a step. An operation that writes or makes a credential always has the approval flag, also when its connector registered it without the flag, and an install or tenant override that turns approval off leaves it on. So a person's call of it waits too, with a token and in the web console. Grant create, run approval create and agent grant create (an exact op id with `auto-execute`) refuse such an operation. A credential read that returns no secret value (`vault.kv.list`, `vault.kv.compare`, `k8s.secret.compare_to_ref`, and `vault.kv.read` without `reveal_secret`) still runs at once. Inside a multi-step run, MEHO does not store the result of a step that reads, writes or makes a credential. When a later step of that run waits for a person, the run goes on after the approval as the row `composite-resume-steps.md` says. A credential write or make that ended well is not sent again. A Vault read that needed no person (`vault.kv.read`, `vault.kv.list`, `vault.kv.compare`) is sent again when it still needs none. A run with any other credential read before the waiting step stops with `composite_resume_read_not_sent`, and MEHO makes no approval request.

## Action
Find the grants that name such an operation with `meho service-principals grants list`, `meho agent grant list` and `meho approvals runs list`, and remove them or leave them. An automation run that writes or makes credentials waits for a person on each such call: approve each call in the console or the CLI. No schema action.

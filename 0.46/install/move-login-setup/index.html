    Move the login setup to another install¶

    Use this page when you move MEHO to a new install, for example to another install form or to a new machine. It moves the login setup that lives in Keycloak:

    • the identity providers (for example Entra ID),
    • the directory connection (Active Directory or LDAP),
    • the groups, with their attributes,
    • who is in which group.

    The settings file does not carry any of this. You move it with Keycloak's own partial export and partial import, and do a few steps by hand. MEHO has no command for it.

    What Keycloak's partial export leaves out

    • Secrets. Keycloak replaces every secret with * characters: the client secret of an identity provider and the bind password of a directory. You type them again on the new install.
    • People. The export has no users, so it has no group members.
    • The directory connection. The export file has it, but the partial import does not read it. You add it again by hand.
    • The identity provider mappers. The export file has them, under identityProviderMappers, but the partial import does not read them. A mapper puts people from an identity provider into their group. You add each one again by hand.
    • The second login step. The partial import does not bring login flows, so a code from an authenticator app is not asked for until you set it up again. The people's authenticator apps do not move either: each person sets up the app again at their first login.

    Keycloak itself says the admin console export is not a backup, and not meant to move a whole realm. Here you use it only for the groups and the identity providers. You add the rest by hand.

    Before you start¶

    • The old install still runs. You read from it in step 1 and step 6.
    • A Keycloak admin login on both installs. See The console admin, or Keycloak break-glass when nobody can log in.
    • The same tenant values in the new install. Give the new install the same Helm values as the old one for coreKeycloak.firstTenantId, coreKeycloak.tenantName and coreKeycloak.tenants. Then the new install makes the same role groups, with the same tenant ids. The tenant ids must also match the ids in your settings file.
    • The company login values. When the old install sets up its company login with Helm values (coreKeycloak.companyLogin: Entra ID, authentik, your own Keycloak), copy these values to the new install. Make the Secret with the client secret on the new install too. The new install then sets up this login by itself. When the new install has another address, add its redirect URI in your login system (see the recipe in Company login).
    • A Keycloak target in MEHO on the new install, for step 6. See Add a tenant.

    1. Export from the old install¶

    In the Keycloak admin console of the old install, open realm meho:

    1. Click Realm settings.
    2. Open the Action menu (top right) and pick Partial export.
    3. Turn on Include groups and roles. Leave Include clients off: the new install makes its own clients.
    4. Click Export. Keycloak saves the file realm-export.json.

    On a realm with many groups, the export can make Keycloak slow for a short time. Do it at a quiet time.

    The file has no secrets, but it shows how your login is built. Keep it in a safe place, and delete it when you are done.

    2. Import into the new install¶

    In the Keycloak admin console of the new install, open realm meho:

    1. Click Realm settings.
    2. Open the Action menu and pick Partial import.
    3. Pick the file realm-export.json.
    4. Pick only Groups and Identity providers. Do not pick clients or roles: the new install made its own, and they must stay as they are.
    5. For a resource that already exists, pick Skip. Then the groups and the login the new install made stay as they are. Keycloak adds only what is missing. Note: when a group already exists, Keycloak skips it with its sub-groups. Add a missing sub-group by hand.
    6. Click Import.

    Check in Groups that every group of the old install is there, with its attributes.

    Then add the identity provider mappers again. The partial import did not bring them, so people from these identity providers get no group, and MEHO refuses their login. For each identity provider you imported:

    1. In the old admin console, open Identity providers, open the identity provider and click the Mappers tab. Note each mapper: its name, its type and its values. You can also read them in the export file, under identityProviderMappers. Each entry there names its identity provider in identityProviderAlias.
    2. In the new admin console, open the same identity provider, click Mappers, and add each mapper with the same values.

    An identity provider that the Helm values set up needs nothing here: the new install made its mappers.

    3. Add the directory connection again¶

    Only when your people come from Active Directory or LDAP.

    Follow the recipe Active Directory / LDAP on the new install:

    • step 2, "Connect the directory",
    • step 3, "Bring the directory groups in",
    • step 5, "Add a second login step", when the old install asks for a code from an authenticator app. To check this, open Authentication in the old admin console and look at the flow marked Used by: Browser flow. Do this step now, before step 4: nobody can log in through the directory until step 4 types the bind password, so nobody logs in without the code.

    Use the same values as on the old install. You can read them in the old Keycloak admin console under User federation, or in the export file. The bind password is not in the file: type it in step 4.

    4. Type the secrets again¶

    The export has * characters in place of each secret. Type each one again on the new install, before anyone logs in:

    • Each identity provider you imported in step 2: in Identity providers, open it and type the Client Secret again. An identity provider that the Helm values set up needs nothing here.
    • The directory connection from step 3: in User federation, open it and type the Bind credentials again. Click Test authentication.

    5. Check the logins¶

    Log in once with a person from each login system: a person from the directory, a person from each identity provider. A person who comes from the directory or from an identity provider gets their group from there. Check that each one gets the right tenant and role.

    When the old install asked for a code from an authenticator app, check that the new install asks for it too. The first login of each person asks them to set up the app. Every later login asks for the code. If a login works with the password only, stop and do step 5 of the recipe Active Directory / LDAP before anyone else logs in.

    6. Add the other group members¶

    Only the people who do not get their group from a directory or an identity provider. For example, people you made by hand in Keycloak.

    1. On the old install, list the members of each group:

      meho keycloak group list --target <keycloak-target> --json
meho keycloak group member list --target <keycloak-target> \
  --id <group-id> --max 100000

      Always pass --max. Without it, Keycloak returns only the first 100 members, and the count MEHO shows counts only these. Pick a number larger than your biggest group. When the list has exactly that many members, the list may be cut: run it again with a larger number.

      Then check the list is complete. In the old Keycloak admin console, open Groups, open the group and click the Members tab. Leave Include sub-group users off. The tab shows a few members per page: page through to the end, and check that each member there is on your list.

    2. On the new install, each person must exist first. Make them as in Add a tenant.

    3. On the new install, add each person to their group:

      meho keycloak group member add --target <keycloak-target> \
  --username <username> --group-name <group-name>

    Each add waits until a person approves it. A group decides a person's tenant and role, so MEHO never adds a member without approval. The box at the top of Add a tenant says who may approve.

    Put each person in exactly one role group (see the rules).

    What else moves, and how¶

    • MEHO's own settings (policies, conventions, targets): with the settings file.
    • Passwords of targets and keys: with the backup of your password safe. See Back up, restore and update.

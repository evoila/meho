## Note
The guide for your own Vault (`coreVault.enabled: false`) gives one policy recipe: the per-tenant policy, so each tenant reads only `secret/tenants/<tenant id>/`. The `meho-mcp` login role in the guide is bound to the audience and to the addresses MEHO uses (`token_bound_cidrs`), and has `token_ttl=5m`. Only MEHO needs to reach the Vault login path. The built-in OpenBao is not changed.

## Action
If you bring your own Vault, keep your current policy and its grants until every step below is done, and do the steps in this order. (1) Set up the Vault login of every person and every agent that uses MEHO: the tenant metadata on its Vault entity and a place in the tenant's role group, as part 3 of [the Vault provisioning guide](https://github.com/evoila/meho/blob/main/docs/cross-repo/vault-provisioning.md) says. A Vault entity holds one tenant. A person who works in more than one tenant (`meho tenants use`) needs a separate login identity for each tenant: setting the tenant metadata a second time replaces the first tenant. (2) Apply the per-tenant policy from the same guide next to the current policy, so each login reads both the old paths and its tenant folder. On the `meho-mcp` role, set `token_ttl=5m`, and set `token_bound_cidrs` to address ranges that cover every address MEHO uses to reach Vault: the pod network range, or every node address or the outbound address when the traffic is translated (behind a proxy, bind the address Vault sees). If Sensors check targets, add the new paths to the policy of the check runner's role (`VAULT_CHECK_RUNNER_ROLE`) too, and keep its old paths. (3) Do the inventory for each tenant: run `meho tenants use <tenant>`, then `meho targets list --json --limit 500`. The list shows one page of the current tenant only: when a page has 500 targets, run it again with `--cursor <name of the last target on the page>` until a page has fewer. Move each target whose `secret_ref` is a Vault path outside `tenants/<tenant id>/`. A target with an empty `secret_ref` or a `gsm:` ref stays as it is. (4) For each target to move, copy the secret to `secret/tenants/<tenant id>/<target>` and run `meho targets update <name> --secret-ref tenants/<tenant id>/<target>`. This command only asks for approval and exits 0: a person must approve each request (or make the change in the web console, where it applies at once). Then check with `meho targets describe <name>` that the target shows the new `secret_ref`. Then check that MEHO reads the moved secret: run a read-only operation on the target. `meho targets probe <name>` alone does not prove it, because some connectors probe without a login. For a target that a Sensor checks, also wait for the next scheduled run of that Sensor and check that it shows a real state, not `unknown`. The steps and commands are in [the per-tenant migration guide](https://github.com/evoila/meho/blob/main/docs/cross-repo/vault-per-tenant-migration.md). (5) Before you remove the old grants, check the read in each tenant with the login of each person who works there, also when one login works in more than one tenant. Remove the old grants (of the `meho-mcp` policy and of the check runner's policy) only after every target of every tenant shows its new `secret_ref`, passed the read check and, when a Sensor checks it, the Sensor check. Without the per-tenant setup, each read of a person or agent fails after the old grants are gone, while the health check still passes. Then check that `GET /api/v1/health` still shows `vault.read_ok: true` and that a read-only operation still works on each target.

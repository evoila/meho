## Note
More calls wait for a person on every call, and no standing grant, no agent grant and no run approval covers them: a `proxmox.api.get` of a path that reads inside a guest (a guest agent read such as `file-read` or `exec-status`, the cloud-init data, a file from a backup), opens a console, or can return a stored secret (ACME plugins, webhook endpoints, metric, IPAM and DNS servers, an auth realm, the subscription); a `k8s.apply` of an object that runs a pod (`Pod`, `Deployment`, `StatefulSet`, `DaemonSet`, `ReplicaSet`, `ReplicationController`, `Job`, `CronJob`, `PodTemplate`), gives rights (`Role`, `ClusterRole`, `RoleBinding`, `ClusterRoleBinding`) or makes or reads a Secret (`ExternalSecret`, `ClusterExternalSecret`, `SecretStore`, `ClusterSecretStore`, `PushSecret`, `SealedSecret`, `Certificate`); and the operations made from an ingested Kubernetes API file that read or write a Secret, run a command in a pod, open a proxy or a port forward, make a token, or write a pod, a workload, a role or a binding. A person's own call of these waits too. Plain Proxmox reads and an apply of other kinds keep their rules. The card of a `k8s.apply` shows a person what each container runs. A `k8s.apply` of a Secret keeps its manifest only in the encrypted handoff, so it needs `APPROVAL_HANDOFF_ENCRYPTION_KEY` like every credential write; without the key MEHO refuses the call. A sensor of a call that waits is refused at create and reads `unknown`. Who waits now: a run, a service login, an agent or the automation engine that used a standing grant or a run approval to apply workloads or roles, or to read inside a guest, now waits for a person at that call.

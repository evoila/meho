## Note
The guide for your own Vault (`coreVault.enabled: false`) gives one policy recipe: the per-tenant policy, so each tenant reads only `secret/tenants/<tenant id>/`. The `meho-mcp` login role in the guide is bound to the audience and to the addresses MEHO uses (`token_bound_cidrs`), and has `token_ttl=5m`. Only MEHO needs to reach the Vault login path. The built-in OpenBao is not changed.

## Action
If you bring your own Vault, keep your current policy until your target secrets are in the tenant folders. First list your targets with `meho targets list --json` and find each `secret_ref` that does not start with `tenants/<tenant id>/`. For each one, copy the secret to `secret/tenants/<tenant id>/<target>`, point the target to it with `meho targets update <name> --secret-ref tenants/<tenant id>/<target>`, and check that `meho targets probe <name>` still reaches the target. The steps and commands are in [the per-tenant migration guide](https://github.com/evoila/meho/blob/main/docs/cross-repo/vault-per-tenant-migration.md). Then apply the per-tenant policy from [the Vault provisioning guide](https://github.com/evoila/meho/blob/main/docs/cross-repo/vault-provisioning.md), set `token_bound_cidrs` on the `meho-mcp` role to the addresses MEHO uses to reach Vault (when MEHO reaches Vault through a proxy or address translation, bind the address Vault sees), and remove the old grants. Check that `GET /api/v1/health` still shows `vault.read_ok: true` and that `meho targets probe <name>` still reaches each target.

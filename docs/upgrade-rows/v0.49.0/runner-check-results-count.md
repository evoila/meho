## Note
With the new setting `RUNNER_CHECKS_ENABLED=true` (off by default), a check that has a `runner_name` runs on that runner at its site, and the result the runner posts counts like the result of a central check. It sets the state, shows on the dashboard ("runs at: runner `<name>`"), sends mails on a change and on recovery, and can start the investigator. MEHO reads the rule of the check on the answer, so a runner never sends a state. An answer over 256 KB, or a batch over 4 MB, gives the check the state `unknown` with the reason "answer too large". A result needs the runner's own time: a runner time later than MEHO's clock is refused and named in the answer, and a result without one is stored but not counted. The runner runs each check on the check's own schedule. When a runner stops reporting, its checks read `unknown`. With the setting off, MEHO only stores runner results, the answers do not show `runner_name`, and the clean-up job deletes no runner results. Migration `0187` adds the nullable `sensor.runner_name` and `sensor.runner_produced_at` columns and an index on `runner_check_results.received_at`. A new setting `RUNNER_CHECK_RESULTS_RETENTION_DAYS` (default 7, `0` keeps all) sets how long the clean-up job keeps raw runner results while `RUNNER_CHECKS_ENABLED` is on. See https://evoila.github.io/meho/latest/guides/satellite-gateway/#checks-that-run-at-a-site.

## Action
None. The setting is off by default, and the migration runs at start. To run checks at a site, update the runners first, then set `RUNNER_CHECKS_ENABLED=true` and create the check with `runner_name` (`meho sensor create --runner <name>`).

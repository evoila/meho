## Note
When a multi-step operation waits for approval at one of its steps and goes on after the approval, MEHO does not send the steps that already ran again. MEHO stores the steps of the run, with their results, on the approval request and replays them; the result of a step that reads, writes or makes a credential is never stored. **These runs finish:** a run with a credential write or make that ended well (it is not sent again and gives back no result); a run with a Vault secret read (`vault.kv.read`, `vault.kv.list`, `vault.kv.compare`) that needed no person and still needs none (it is sent again after the approval). **These runs stop:** a run with any other credential read before a step that needs approval, also a read that stores a value, that a person approved or whose policy now needs a person (`composite_resume_read_not_sent`, which names the read; no approval request is made); a run with a step whose end MEHO does not know, also a credential write with a lost answer (`composite_resume_step_outcome_unknown`); a run whose read gives a new answer that changes the approved step (`composite_resume_repeats_write`; that step is not sent). A second step that waits in the same run waits for its own approval (the error `composite_resume_multi_gate_unsupported` is gone). A request of a step of a multi-step operation is never run again through `POST /api/v1/approvals/{id}/rerun` (refusal `multi_step_run`, which replaces `input_not_kept`). Connector authors run each change of a multi-step operation that can go on after an approval through `run_governed_subop`.

## Action
A multi-step run that waits for approval at the upgrade does not go on: its request expires at start-up like every request of the older release, and an approved one that has not run yet is refused. The requester starts the operation again.

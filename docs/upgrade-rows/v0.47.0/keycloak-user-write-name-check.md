## Note
After approval, the Keycloak user writes act on the user id that the approval card shows. They do not look the username up again. This covers 13 operations: `keycloak.user.disable`, `.enable`, `.reset_password`, `.logout`, `.delete`, `.update`, `.required_actions.update` and `.credential.delete`, `keycloak.role_mapping.assign`, `.client.assign` and `.client.remove`, and `keycloak.group.member.add` / `.remove`. The approved run is refused, and nothing is changed, when the card shows no stored username (the user could not be read when the request was made), or when the username stored in Keycloak now is not the one on the card (the user was renamed while the request waited). This holds for a request by id, by username, or by both. The results of these writes show the username that is stored in Keycloak. A request for one of these operations that waits for approval at the upgrade is refused when it runs, also one that was sent by id only: its card from before the upgrade does not show the stored username, or has no user id. For `keycloak.user.delete` this holds when its card shows no username or said that the user does not exist.

## Action
Send these requests again after the upgrade. Requests made after the upgrade are not affected by the upgrade.

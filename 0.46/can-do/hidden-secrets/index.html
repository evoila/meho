    Secret values stay hidden¶

    An agent or a person does not see a password, a token or a key in the result of an operation.

    What it does¶

    MEHO hides secret values in three places:

    • In answers. Every operation hides the value of each secret-named field in its answer, for example password, token, api_key or client_secret. This holds for the result, for the sample rows, and for the rows behind a result handle. Secret reads show the names of the keys, not their values.
    • In previews and approvals. The preview of a change that waits for approval hides secret values. In a link, MEHO hides the user and password part and the values of signature, credential and token parameters. A decided approval request keeps no secret values.
    • In traces and records. The flight recorder, the audit log, error text from a vendor and broadcast messages hide secret values too. The audit row keeps a keyed fingerprint instead of the value. Two equal values still give the same fingerprint, so you can see a repeat without seeing the secret.

    More rules:

    • MEHO also finds secrets in free text, for example private key blocks and labels such as DB_PASSWORD=.
    • A person or a service principal can ask for the real value with reveal_secret: true. An agent is refused. When the operation reads a secret, such as a Vault secret read, the request waits until a second person approves it. For every request with reveal_secret that waits for approval, also one that creates a credential, approving does not run the operation. The person who asked then runs it and gets the value. This works once, and only for 15 minutes after the approval. The person who approved does not see the value, and MEHO does not store it. No browser or proxy keeps the answer with the value: it says Cache-Control: no-store. The same is true when a person sees the values at once, on a read that needs no approval.
    • A call with reveal_secret: true cannot run in the background. With async: true it is refused. It runs at once, or through an approval.
    • How the person who asked gets the value:
      • Command line: meho secret read --approval <id> --field <name>.
      • Console: "Show value" in the Vault view.
      • REST: POST /api/v1/approvals/<id>/reveal.
      • MCP (an AI tool such as Claude Code): call call_operation again with the same connector_id and op_id, and approval_request_id: <id>. Send nothing else. This needs the switch MCP_REVEAL_FETCH, which is off by default. With it off, a person who works through MCP uses the command line or the console.
      • A second try is refused, and it shows no value.
    • An operation that makes a new credential still gives it to the caller once.
    • A connector can mark a field that only looks secret, such as a date or a count, so that it stays whole.

    Product versions¶

    This works for every connector and every product version. It is a rule of the MEHO core, not of one connector.

    State¶

    • Shipped from v0.40.0, and extended in each release up to v0.45.0:
      • v0.40.0: secret reads show names, not values.
      • v0.42.0: every operation hides secret-named fields in its answer.
      • v0.43.0: a decided approval request keeps no secret values.
      • v0.44.0: more values are hidden in answers, previews and records.
      • v0.45.0: link secrets are hidden in approvals and traces. The Azure connector masks keys in traces.
    • The What's new page has the details of each release.
